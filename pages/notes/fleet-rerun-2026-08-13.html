June fleet rerun: the v1 recipe bug, fixed on the grid

2026-08-13 · June cosmic bench · wft campaign

184 of the 214 campaign rows were reconstructed on the wrong track selection. Their reference files are tracking v1, and the LCG_105 stack on the lxplus workers mis-resolves those files' NClus branches — so the jobs silently dropped NClus ≥ 4 and effectively ran χ²-only. On the 16 tier-A rows affected, 55.4 % of the 116,776 events they reconstructed fall outside the frozen recipe (43–69 % per row). Not a thinning: a different recipe, in both directions.

The fleet has been rebuilt with every job carrying a matched event list computed locally, so no worker opens a rays file at all. 156 grid jobs, 21 rows promoted, tier B working for the first time. The five detector headline numbers are unchanged — and that is the expected result.

Why the headline numbers did not move

All five golden keys have m3_tracking_root_v2 reference files, so the bug never touched them. That is also why it survived a whole campaign: the conference digest and the det6/det7 audit only ever looked at rows that were immune. The corrected recipe lands on the 144 v1 rows that feed the scan and digest tables, not on the five detector pages.

What did change for these keys is where the per-plane angle constants are applied. w0/kw are now applied inside the fit and stamped in the output metadata, rather than patched on afterwards. Angle bias is |≤ 0.20°| on every fleet plane, against a Y-heavy bias reaching −1.04° when the constants were being dropped entirely.

The fix: the worker never reads a rays file

Reconstruction needs exactly one thing from the reference tracker — which event ids to fit. Reference positions are attached later, by stages that run locally. So the event ids are computed here, where a modern uproot reads v1 files correctly, and shipped with the job:

  • make_matched_lists.py writes one matched_row<NNN>.json per row, recording the recipe it used.
  • run_reco_job.py --matched-list refuses any list whose recipe, row index or key disagrees with the row it was handed.
  • Rows that cannot be listed are refused, not downgraded.

This removes the failure mode rather than avoiding it: there is no longer a code path in which a worker's stack decides what the recipe means.

Three defects found while building it

Condor splits queue items on whitespace, not just commas

Only the last queue variable absorbs the remainder of the line. With the extra-arguments column in the middle, all 151 jobs would have gone out as extra="--bundle-name" with the rest swallowed into the file transfer request. condor_submit -dry-run caught it before submission; column order is now row,tag,mlist,extra.

The phase-2 gate was being ignored for the golden keys

mx17_2 and mx17_4 adopted the t0 prior, but their golden prod arm was still built on the base bundle — promoting it would have put those two detectors' reference runs on the un-adopted configuration while every other row of the same detector used _t0p. The local rerun had the same gap; six products were discarded and redone. Verified against every promoted product's metadata rather than against the submit files.

Tier B had never worked at all

All seven --vrefit rows are missing from the previous generation's outputs too. Two independent blockers: the calibrator was invoked through runpy as __main__, so its process pool could not pickle its own worker function; and the six drift-scan points had no alignment on disk. The run registry already said how to handle the second — the long run seeds the scans — so z, rotation and handedness are inherited and only the translation is refitted. The points land within 0.04 mm of the seed, which is the check that the seeding is legitimate: the detector did not move between scan points.

Tier B is held back for a specific reason: a refit bundle carries no w0/kw — the calibrator has no notion of them — so those tables' angles are on the uncorrected mapping and are not quotable. Their velocities are. The promoter now enforces this rather than relying on anyone remembering it, and equally refuses off-conditions rows and comparison arms.

Grid and local agree

The same rows were reconstructed both on a worker and on the laptop, from the same commit, bundles and lists:

  • Row 103 (176 events): agreement to 3.3×10−14 relative — floating-point summation order. Geometry columns identical to the last digit.
  • Row 20 (19,233 events): identical event set, worst relative difference 2×10−5 on fit-error columns and 4×10−6 on y_tan_theta — optimizer convergence across different CPUs, negligible for anything quoted.

Still open

  • Row 100 (tier B, v1): needs a hits-chain cache built before it can be v-refitted, and would be unpromotable anyway for the w0/kw reason above.
  • Rows 139/140: the telescope recorded no rays. Nothing to reconstruct, correctly excluded.
  • Row 59 / detector A: reconstructed and validated — the same 22,095-event set as the live reference, same bundle — but left unpromoted per instruction. Adopting it is the only thing between detector A and a fleet that applies w0/kw in-reco everywhere.
