Setting up a simple EOS-backed website at CERN

Written 2026-08-15, from getting dylan-neff.web.cern.ch running. Steps and field names checked against webeos.docs.cern.ch and the CERNBox personal-website page on the day of writing.

The whole thing is two objects: a folder of static files on EOS, and a site record in the Web Services Portal that points a hostname at that folder. Nothing else — no server, no build, no container. Whatever is in the folder is what the web sees.

The step that traps almost everyone is #2 below: the web servers read your folder as a robot account called wwweos, which has no rights to anything of yours until you explicitly share the folder with it. Your own CERN access — however complete — grants that robot nothing. A site whose folder was never shared answers 403 forever while every file looks perfectly readable to you.

1. Make the folder, put something in it

On lxplus, in your EOS home (substitute your username; the letter is its first initial):

ssh lxplus
mkdir -p /eos/user/a/asmith/www
echo '<h1>hello</h1>' > /eos/user/a/asmith/www/index.html

The folder name www is a convention, not a requirement — the portal asks you for the path explicitly. What is required is that the path you give the portal is the directory containing index.html, not its parent.

Everything is served as a plain file. Subdirectories work and /x17/ resolves to /x17/index.html. There is no PHP, no CGI, no database — if the page needs to compute something it does it in JavaScript in the reader's browser, or you generate the HTML before uploading.

2. Share the folder with wwweos — the step that is actually the problem

The web front end reads EOS as the service account wwweos. Grant it read access to the folder you just made:

  1. Open CERNBox and navigate to the www folder.
  2. Share it. In the sharing search box, switch the dropdown to Service Accounts — wwweos will not appear in the normal people search.
  3. Pick wwweos, set the permission to Can view (Viewer — read-only is exactly right; it never needs to write), and click Share.

Share the folder you named in the portal, not its parent, and not one file. Sharing your whole EOS home instead of www is the common near-miss: it may look equivalent, but the site is configured against the www path and that is what has to carry the grant.

If you later move the site to a different EOS location, the new location needs its own share with wwweos. Changing the path in the portal does not carry the permission across, and the symptom is a site that was working and abruptly 403s.

CERN's own knowledge-base article for this folder configuration is KB0004096, if you need something to cite in a ticket.

3. Create the site record

Go to the Web Services Portal (webEOS), logged in as the account that will own the site — only CERN primary accounts can own one, so this will not work from a secondary or service account. Fill in:

FieldWhat to put
Site Category Personal for your own page. Official is for a project, team or collaboration; Test is for something temporary.
Site Name 4–63 characters, lowercase letters, digits and dashes only, starting and ending alphanumeric. This becomes the hostname. It is independent of your username — mine is dylan-neff while the folder lives under dneff. Pick the readable one; you are stuck with it.
Subdomain.web.cern.ch (the alternative, .docs.cern.ch, is for documentation sites).
Site DescriptionMandatory. One sentence on what the site is for.
EOS Path /eos/user/a/asmith/www — the directory holding index.html. Permitted roots include /eos/user/, /eos/project/, /eos/experiment/ and the experiment areas (/eos/atlas/, /eos/cms/, /eos/lhcb/, …).

Submit, then wait a few minutes — DNS has to propagate, and a fresh site answers with nothing at all until it does. A site that 404s or fails to resolve in the first five minutes is not evidence of a mistake.

4. Decide who can read it

This catches people out in the opposite direction: the default is not public. Out of the box the portal creates a default-role that admits CERN and eduGAIN authenticated users, so an outside visitor gets an SSO login screen rather than your page.

  • Public site (a CV, a project page you cite in a paper): enable Guest Access in the portal. Unauthenticated visitors then get the page with no login screen.
  • CERN-only: leave Guest Access off. That is the default.
  • A specific e-group: done in the Application Portal, under the registration named webframeworks-webeos-<sitename>. Uncheck "this role applies to all authenticated users" on the default role and map the role to your group(s) instead.

Access control here applies to the whole site, which is worth knowing before you plan around it: you cannot leave a public CV at / and put a restricted page at /internal/ through this mechanism. HTTPS is enforced by default; there is nothing to configure for it.

5. Push updates from your laptop

Two options, and they are not exclusive.

CERNBox, for the occasional file

Drag files into the www folder in the CERNBox web UI, or sync it with the CERNBox desktop client and edit locally. Nothing else needed — the site serves whatever is in the folder.

rsync over lxplus, once it is a real site

What I use. Keep the site in git on your laptop and push the built files up:

kinit asmith@CERN.CH                    # Kerberos ticket, forwarded to lxplus
rsync -rvz --no-perms --no-owner --no-group --omit-dir-times \
      index.html style.css js assets \
      lxplus:/eos/user/a/asmith/www/

Three things that are easy to get wrong, all learned the hard way:

  • -r, not -a. The EOS FUSE mount rejects chown and most permission- and timestamp-preservation, so -a produces a wall of errors on files that actually copied fine.
  • Never --delete, and list what you push explicitly. The web root can hold things your repo does not own. The corollary is that rsync never removes anything: rename or delete a file locally and the old copy stays served at its old URL until you ssh lxplus 'rm /eos/user/a/asmith/www/old.html' by hand.
  • "Permission denied" on /eos usually means a stale ticket, not a broken share — an expired Kerberos credential held open by a persistent SSH master connection. Run ssh -O exit lxplus to drop the master, then retry the kinit and the push.

When it looks broken

SymptomAlmost always
403 Forbidden, but you can read every file yourself The wwweos share (step 2) is missing, was made on the wrong folder, or was lost when the EOS path changed. Your own access is irrelevant to it.
Site asks for an SSO login and you wanted it public Guest Access is off — the default. Step 4.
404 on the front page, other files fine The EOS Path points at the parent of the directory holding index.html, or the file is named something else.
Nothing resolves at all, minutes after creating the site DNS propagation. Give it five minutes before debugging anything else.
A file serves with the wrong type, or the browser refuses it The server maps types by extension and its table is narrower than your local preview's. .webmanifest, for instance, comes back with no Content-Type header at all — renaming that file to .json fixed it for me. Test with curl -sI https://yoursite.web.cern.ch/file against the deployed site: python3 -m http.server knows more MIME types than the real server and will happily hide this.
Redirects or auth rules in .htaccess ignored .htaccess files are read only if you enable Use .htaccess files under Site Access in the portal.
An edit does not show up Check the file really landed (ssh lxplus ls -l …/www/) before blaming a cache; then hard-reload.

Working locally

Because it is all static, the site runs on your laptop with no infrastructure:

python3 -m http.server -d . 8000     # http://localhost:8000

That is a faithful preview of layout and behaviour. It is not a faithful preview of headers, MIME types, or anything access-control-related — check those on the deployed site.

The short version

  1. mkdir /eos/user/a/asmith/www, put an index.html in it.
  2. CERNBox → share that folder with service account wwweos, Can view. ← the one that bites
  3. Web Services Portal → new webEOS site: Personal, a name, .web.cern.ch, a description, that EOS path.
  4. Guest Access on if it should be public. Wait a few minutes for DNS.
  5. Update it with CERNBox, or rsync -rvz --no-perms … to lxplus:/eos/user/a/asmith/www/.

Reference: webeos.docs.cern.ch (creating, managing, authorization) and CERNBox personal websites. If the site itself is fine but EOS is not cooperating, the Service Portal ticket goes to the Web Services team; a share that will not stick is an EOS/CERNBox problem.
