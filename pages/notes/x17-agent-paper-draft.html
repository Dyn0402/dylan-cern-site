A general-purpose coding agent as the control and analysis layer of a bespoke neutron-beam experiment

MX17 at n_TOF EAR2, 28 June – 10 August 2026. What the archive supports, what it does not, and what we propose to write.

Dylan Neff · CEA Saclay / Univ. Manchester · drafted 8 August 2026

The framing, up front

We cannot claim an efficiency improvement. There is no manual baseline: the May beam test used the agent too, no transcripts survive from it, and nobody timed anything. Any “N× faster” claim would be fabricated and a referee would ask for the control.

So the paper is not “agents make experiments faster.” It is an existence proof with a complete method: a bespoke experiment with six incompatible instrument interfaces and no unified control system; exactly what a general-purpose agent was made to do across it during beam; what that cost in code; and where it failed. Every efficiency-flavoured statement in the draft is either attributed to the operator's judgment or cut.

1. The architecture claim

MX17 had no unified control system and was never going to get one. It was assembled in weeks from instruments sharing no protocol, no configuration language and no vendor, and disassembled six weeks later. The agent was given no purpose-built instrument integration — only a shell, the filesystem, the network, and the same vendor SDKs, manuals and source trees a human would have.

The confound we have to separate

Any benefit here is the product of three separable things, and the paper must not let them collapse into one claim.

LayerWhat it providesWould exist without the agent?
Remotely controllable instruments thresholds, delays and gates settable over a network; scalers readable over a network Yes. The N1081B is a commercial product with a documented API.
Scripted automation unattended parameter scans, logging, reproducible configuration Yes. Any competent physicist can write these scripts.
The agent wrote and debugged those scripts, in-session, against live hardware, with no prior familiarity with any of these interfaces —

The programmable-logic modules are the enabling precondition, not a result of this work. Had the trigger been built from fixed-threshold discriminators with screwdriver potentiometers, no agent could have scanned it. Equally, nothing the agent produced is code a physicist could not have written. The claim is narrower and honest: this quantity of integration, across this many unrelated interfaces, was produced and debugged by one person during a running experiment, while taking shifts.

2. The flagship result: automated trigger characterisation

The trigger was six CAEN N1081B programmable logic units on a private network. Analogue detector signals are discriminated in the same units that form the coincidence, and a separate unit counts the results — so both halves of a measurement loop are remote. A Poisson pulse generator (667 Hz) was wired in permanently as a beam-independent debug stimulus.

3. DREAM: reading the firmware when the manual is wrong

The DREAM front-end is configured through a bespoke text format with thin and partly incorrect documentation. On 23 July, three concurrent agent sessions attacked its optimisation and produced five documents; a sixth reconciled them, opening with a warning that intermediate claims had been corrected within the same day and should not be quoted.

The instructive case is a three-way documentation conflict. The FEU manual gives the read-clock divider range as [2;6]; the configuration comment says {3,4,5,6}; the compiled firmware source enforces [4.0;15.5]. The agent resolved it by reading the vendor's C source, and that reading produced the day's only adopted change:

7,231 → 10,847Hz readout, zero drops
1.5×read-clock gain, free
100%tracer channels retained

The same source read surfaced an explicit vendor prohibition in a comment — “Never touch Dream registers 10 and 11” — closing off another proposed optimisation before it was tried. Reading compiled firmware source to establish real limits is exactly what a scaffolded, tool-bounded agent cannot do, and it is a direct answer to the objection that shell-level access is merely unsafe rather than also more capable.

Equally worth reporting: the day's yield interpretation flip-flopped, and one session refuted its own model using flash-anchored run data, settling on the conservative answer — the read clock buys headroom, not yield — with an explicit instruction not to quote it as a yield gain.

4. What the integration actually cost

No baseline is needed to report this: it is a description of the system, not a comparison.

The Keithley integration is the least agent-shaped task in the paper and instructive for that reason: reading ³He pressure required building the whole linux-gpib stack from source against a modern kernel, including a kernel module. The agent could not do it — it cannot type a sudo password, because the tool interface is non-interactive. The setup guide it wrote for itself opens with that as a ground rule and hands every root step to the human.

6. Supervision — the uncomfortable finding

We reconstructed what the agent was actually permitted to do from settings files and session records, rather than from intent.

MachineHardware authorityTechnical guardrail
mx17-daqwired to the detectors, HV, gas None. No hooks key ever existed in either settings file; dangerous-mode prompting disabled. Convention only.
analysis laptopnone A PermissionRequest hook routing approvals to the operator's phone, plus a ~50-entry command allowlist.

The machine with hardware actuation authority had the weaker technical bound. We report this because it is what supervision looks like under beam pressure, and because the inversion is probably common and rarely admitted. Where a boundary did hold — privilege — it held because of a tool limitation, not a safety design.

7. What the record lost

The natural answer to “a shell-level agent has no auditable tool surface” is that the session transcript is the audit trail. We tested that against our own archive and it does not fully hold.

The first five days of the beam run have no transcripts on any machine, and the entire May commissioning campaign is gone at transcript level.

The recommendation that costs nothing

If you intend an agent's record to be evidence, configure retention before the first session. Prospective archiving is the only reliable option; the default is designed for privacy, not reproducibility, and nothing warns you. We would have benefited from this enormously, and we are reporting it because nobody else has tried to reconstruct an agentic run after the fact.

8. Limitations, stated plainly

  1. N=1, one operator, no control. Nothing separates the agent's contribution from the operator's skill.
  2. No efficiency measurement, and we do not estimate one.
  3. Self-assessment. This paper is written with the tool it evaluates, about a record of that tool's own work, by the person who directed it. Mitigations: the archive manifests enumerate their own gaps; the reconstructed logbook records 93 conflicts between machine evidence and the contemporaneous human notes; and an adversarial pass over the original project brief falsified several of its claims, which are corrected rather than repeated.
  4. A moving target. The two machines ran different models and the client updated several times mid-run. The system described is not one system.
  5. The instruments were remotely controllable to begin with. On an experiment whose parameters are set by hand, none of this transfers.

9. Outstanding before submission

  1. Final mx17-daq capture — the machine is being unplugged, and two flagship N1081B git branches exist nowhere else.
  2. The replayability test. Take 2–3 surviving sessions and establish whether the record is complete enough to reconstruct what was done to the hardware and why. This is the evidence for the whole auditability argument and it has not been run. Reporting honestly that it partially fails would be more valuable than not testing.
  3. The failure catalogue. Instances exist; a systematic taxonomy does not.
  4. Sessions-to-working-state per interface — the one integration-cost number that needs no baseline.
  5. The physics paragraph on the converged trigger configuration.
