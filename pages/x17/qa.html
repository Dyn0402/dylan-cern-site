Every run the Micromegas DAQ recorded, checked against what is actually archived on EOS: how long it ran, how much of it is there, and how far it got through the processing chain. Built by walking the archive itself, not by trusting a logbook. As of 13 August 2026 every run that recorded data is fully processed — 160 of 161, the exception being one run that recorded none. The n_TOF runs underneath these, and the join between the two, are checked separately.

What is actually being checked

Each raw file the DAQ writes is one (acquisition, FEU) pair — an acquisition being a timestamp and a file number, because a sub-run that was stopped and restarted has two of them sharing file number 000. So every processed product has an exact expected count rather than an approximate one, which makes the coverage check arithmetic rather than judgement:

  • decoded = rawevery raw file was decoded
  • hits = decodedevery decode produced hits
  • combined = acquisitionsevery acquisition was FEU-combined

Pedestal runs are excluded from all four counts. That is less obvious than it sounds: the early runs took their pedestals as an ordinary acquisition, so those files are named datrun despite being pedestals, and they were carried through decoding and hit finding like any other data. Counting them made the earliest runs report half their files undecoded when nothing at all was missing — which is how this survey found the convention in the first place.

A run is fully processed when all three hold on every sub-run, partly processed when a product is short, and raw only when nothing but the raw stream is on disk.

“Partly processed” is not “broken”. Many runs here were configuration studies — watermark ladders, clock scans, threshold ladders — that were deliberately never pushed through the full chain, and a run whose raw files are all present has lost nothing: it can be reprocessed at any time. The alarming case would be raw files missing, which is a different question and is why the raw count is shown separately in each run's detail.

An acquisition of 0-byte files is not a processing gap, and is not counted as one. This is the subtlest thing on the page and it cost two passes to get right. Eight sub-runs across seven runs each had one acquisition whose eight FDFs were all zero bytes, and because a zero-byte file cannot be decoded, each read as “one acquisition never decoded” — a run reported as partly processed on the strength of files containing nothing. There are two causes, both benign and both confirmed against the DAQ's own RunCtrl logs: the DAQ opened a file-roll segment at the boundary and the run ended before anything was written to it (the other twelve segments of those sub-runs are ~200 MB each and their logs show the acquisition completing normally), or an acquisition ran its full length and saw no triggers at 0.00 Hz, which is a quiet detector rather than a lost file. Empty acquisitions are now excluded from the raw and acquisition counts and reported separately, so they neither inflate the denominator nor re-flag the run on every survey.

Mode is backfilled to the whole campaign. Beam, cosmics and pulser come from beam_type in each run's own run_config.json — the same field, and the same rule, the DAQ's statistics used live — never from matching sub-run names, where a “cos” in a tag means nothing reliable. The shift dashboard only ever knew modes from run_67 on, because that is where its ledger starts; the configuration is archived beside the data for all 161 runs, so every run has one here. Pulser runs are marked not physics and are excluded from the totals: a saturating-pulser ladder posts a million events an hour and would wreck any average it entered.

Scanning is not a mode — it is something a run does while in one. A run sweeps a voltage while running on beam, on cosmics or on the pulser, so the two filters above are independent axes rather than one longer list of modes. Combine them and you get, for instance, the four cosmic runs that bounced the resistive voltage.

A run counts as an HV scan when its HV setpoint map is not the same in every sub-run — again from the configuration, not from names. run_config.json stores the full setpoint map each sub-run was taken at, and detectors[].hv_channels maps each (board, channel) to a role, so the channels that moved name the axis: 44 runs swept the resistive voltage, 20 swept drift and resist together, and the badge on a row gives the number of distinct setpoints. Name matching would have missed most of these: the earliest scans record their trigger note as nothing more than “PS Pickup”, yet the configuration shows them stepping through as many as 101 setpoints.

The test catches deliberate sweeps and two-point “bounces” alike, and it does not flag ladders that swept something other than a voltage — the latency scan, the plastic-threshold plateau, the IPD and jumbo-frame ladders all hold HV fixed and are correctly not HV scans.

Live is not on air. Live hours are the sum of the sub-runs themselves; on-air hours run from the first sub-run's start to the last one's end, so pedestals, HV settling and an operator deciding what to do next all sit inside it. The gap between the two columns is the overhead of running the experiment. Beam-off hours, split by whether the PS or n_TOF was responsible, come from the beam watcher's records by way of the retired dashboard, so they exist only from run_67 on.

Event counts cover the whole campaign, and were recovered rather than assumed. The DAQ's statistics ledger only starts at run_67 — runs 1–66 had been rotated off the DAQ disk before it was created — but the numbers were never really lost: the DREAM RunCtrl log is copied into every sub-run's raw_daq_data/ when the sub-run ends, and it carries the line StopDataTaking OK after total N events in 8 FEUs (M/FEU). Those logs went to EOS with the data. Reading M, the per-FEU count — every event is read out by every FEU, so the FEU-summed N would multiply the campaign by eight — gives an event count for all 2,691 sub-runs that recorded anything.

Where the ledger also has a number, the two are compared: 890 of 891 overlapping sub-runs agree exactly. The one that does not, run_68/cos_003_r540_c00, turned out not to be a disagreement at all. That sub-run holds two acquisitions — one at 15:25 that recorded 1,617 events per FEU, and one at 15:38 that ran its full ten minutes at 0.00 Hz and recorded nothing. The ledger reported the second, this page's log reading reports the sub-run's total. Both numbers are right about different things, which is why the check is quoted here rather than quietly reconciled.

The totals here are therefore larger than the campaign figures on the hub, and deliberately: those count beam triggers from run_67 on, which is what the shift dashboard published all campaign. This page counts every mode of every run, so it adds the 5.4 M events recorded in runs 1–66 — commissioning, HV and threshold scans — plus cosmics and pulser.

Times are UTC, and are the first sub-run's own start — not the file modification times on EOS, which record when the backup copied the data and for the early runs is days after they were taken, and not the configured start_time either. That field is a bare local string with no zone on it, and on a run that was configured and then started hours later it is not when the run took data: it disagreed with the on-air figure beside it by as much as twenty hours. Sub-run timestamps are true epochs, so the start, the end and the on-air span are now all measured from the same thing and on the same clock as the n_TOF table. Both pages read UTC for every reader, in every time zone.
