What is actually being checked

Not whether the run merged. That is the natural question and it is the wrong one. n_TOF’s reconstruction writes one partial per block of raw files and merges them at the end, and a merge can be missing for reasons that say nothing about the data: large runs routinely never merge, and a merged file can exist and be a stub. So the ledger ignores the merge and asks the only question that matters — does the product cover the run?

  • the index treeevery partial carries the run’s full bunch index
  • the last partialits own hits say how far the set actually reaches
  • contiguityno gap in the partial numbering

A run is complete when the partial set spans its own index. On this ledger 442 of 445 are, from n_TOF’s own production. That number was 44 short as recently as 11 August; n_TOF finished the tail block on the evening of the 11th.

An off-recipe product is not coverage. Every product records the UserInput it was built with in its own history object. The campaign recipe is UserInput_2026_EAR2_X17_v4.h, fingerprint e737ed0da496. Seven runs exist here only as our earlier prod_v11, and they are marked off recipe and deliberately not counted — mixing recipes inside one campaign is precisely the mistake this ledger exists to prevent.

We reprocessed 38 runs ourselves, and that is now a cross-check rather than a fallback. They were processed when n_TOF had not yet reached that block. Eight runs now exist in both processings, and on those the comparison is direct rather than statistical: hit for hit, on the same bunches, WAL A–D, PSS A–D, SILI and PKUP are bit-identical on all 22 columns. The liquids agree in hit count with afast differing on fewer than eight hits in a hundred thousand.

One run is genuinely short, and it is not lost. Run 224526’s official product covers 13 % of its beam bunches: 140 of its 167 raw files had expired from the EOS disk buffer when it was reprocessed, and the job built its file list from the 22 that were left. The EOS DAQ/ area is a two-week staging buffer, not the archive — the archive is CTA tape, and all 445 runs are on it, 224526 included, complete and contiguous. The recall is written and verified but has not been fired.

“Still being written” is a real state, not a fault. A run whose reconstruction finished in the last day may still have its partials wiped and rebuilt, and reading one mid-rebuild gets you a truncated file with no error. The state column carries n_TOF’s own settled test: finished means a non-empty merged file that has been left alone, stable but unmerged means a complete partial set untouched for over a day, and still being written means do not read it yet.

Two traps make a healthy run look broken, and both are why the beam state is carried here at all. First, the official runs next door to our block have no beam — 224678–224687 sit at zero pulse intensity and zero pickup amplitude — so using one as a control makes our output look four hundred times too busy. Second, empty PS pulses inside a good run have no gamma flash, so every flash-based check flags them; the first partial of 224692 is 75 % empty while the run as a whole is 98 % beam and clean. Every comparison is gated on delivered protons for this reason.

Every time on this page is UTC, and that is not what the DAQ wrote. The index tree stamps each bunch with a local Date and Time — the n_TOF DAQ runs on UTC+2 — and the listing that reads them builds an epoch as though they were UTC, so they arrive two hours fast. The correction is applied once, at freeze time, and was measured rather than assumed: across the 109 runs that also have raw file timestamps, which are true UTC, the difference is a flat −7127 s (p10 −7185, p90 −7080). That is −7200 s plus the minute or so the first raw file takes to finish writing. The whole campaign sits inside CEST, so one offset covers all of it.

Times are not re-rendered into the reader’s own time zone. Doing so would look identical to anyone in Geneva and quietly shift every number for everyone else, which is exactly the class of error the correction above exists to fix. The independent check is the join itself: all 170 joined segments have a DREAM sub-run whose own recorded window overlaps its n_TOF run, by the amount the slim pipeline measured.

Seven runs have no start or end time, for two unrelated reasons, and each row says which. Three (224454, 224461, 224499) have no merged file for the time listing to read — their partials are complete and the runs are fine. The other four (224535, and the end-of-run trio 224716–224718) recorded between one and sixteen bunches, which is not enough to carry a usable timestamp and is deliberately not published as a run that lasted no time.

That trio is where the campaign stops. The last run carrying beam is 224715, which ended at 07:10 UTC on 10 August — 09:10 in Geneva, the morning the run finished. 224716, 224717 and 224718 are end-of-run acquisitions of a few seconds each with no beam in them. n_TOF the facility carries on and its run numbers keep climbing, but those runs belong to other experiments: this table is scoped to our own X17_measurement DAQ directory, not to a run-number range, so it cannot pick them up.

The match column is a different question and has its own page. Whether a run is reconstructed says nothing about whether its beam has been joined to DREAM; that is a per-segment property, it is roughly half done, and the failures have a known cause in our own code rather than in the data.
